## 1. Constraints

1. No default flip without a logged human verdict (ADR 0008). New visual work ships as opt-in URL
   state, a named shot, and an incumbent/variant pair.
2. No second position authority, renderer branch, or contract field for a visual idea. Helpers return
   positions or opaque `data`; hosts apply them through existing seams.
3. Library helpers take ids, sizes, edges and viewport. Run/turn/file/workflow vocabulary stays in
   `app/pi`, `app/demo` or generated scaffolds.
4. Pi test hooks stay stable: `#proof-line`, `#settings-menu > div`, `#surface-buttons`,
   `#depth-mode`, `#focus-primary`, `#attention`, `data-*` state (`tests/shell.spec.ts:23–55`).
5. A helper is "generic" only after a non-Pi host uses it with its own vocabulary and a test asserts
   the boundary (`second-host.test.ts` is the pattern).
6. Use `pnpm`; no fixed sleeps, no global mocks, no `any` in new code. Report failed gates as failed.
7. Human gates (TODO9 verdicts, study pilot) are dependencies, not developer tasks.

files and share one verification run. E1 first: reproduce with a shortened preceding frame sequence,
then fix the cause or record the limit — never retry until green. B2 measures the packed layout (or
labels the simulated metric correctly). Exit: full visual gate result explained, corrected baseline,
new chapters frame with real internal work. Stop rule: if E1 requires a renderer change, split it into
its own plan before continuing.

**Phase 1 — compared opt-ins (M).** Do A2, B3, B4 and A3. Each visual item is one URL state, one shot
pair and one pending ADR 0008 stub. B4 is mandatory because stream stability is the reason
`previous` exists in `chapterPacking`. Exit: vision gate green, three pending pairs, no default flip.
Stop rule: if a pair cannot be captured deterministically, drop the variant rather than weaken the gate.

**Phase 2 — generalize with proof (M).** D1 is the external blocker for any promotion; proceed with C1
only for seams that already have a non-Pi consumer. Promote the shot/catalog shapes by extracting the
data shape and a thin adapter, not by moving Pi controls into the library. Exit: each promoted helper
has a `second-host.test.ts` (or equivalent) case and unchanged Pi e2e.

**Phase 3 — experiment workbench (L).** Start only after E1 is stable and C1 has landed. C2 adds one
`scenario.html` page driven by `?domain=&layout=&preset=`, using the existing domain packages and
generated registry. C3 extends `packages/create-spacegraph/templates/spine.ts` with the same five
pieces Pi owns today. C4 captures the two-domain proof pair. Blast radius before starting: demo
registry counts, demo-atlas frame count, scaffold output and publish-check fixtures all change —
announce and verify them together.

**Phase 4 — final gate and opportunistic cleanup (S).** E2 and E3 only if Phases 0–3 are green. One
final verification run, then record results in §6.

## 8. Follow-up experiment — multi-octave dynamic range (2026-11-23)

Requested after the plan closed: a layout that shows scale itself, not just one LOD at a time.

- **Hypothesis:** drawing one hierarchy at 1× / ½× / ¼× world scale in a single frame makes the
  self-similar structure visible at fit zoom, and zooming into one branch promotes its smallest
  cards to legible detail. This is the first experiment that changes node *size* rather than chrome.
- **Landed:** generic `octaveLayout(ids, parentOf, options)` at `src/layout/octaves.ts:29`, with a
  caller-owned parent map and no vocabulary; opaque per-node scale descriptors on `GraphLayout`
  (`src/layout/strategies.ts:130`); Pi adapter and opt-in mode `octaves`
  (`app/pi/src/graph-layout.ts:150,193`); host applies scale through the existing `size` seam and
  hides scope hulls in that mode (`app/pi/src/host.ts:283,1044,1129`); symmetric shot fixture
  (`app/pi/src/fixture.ts:123`); two named shots (`app/pi/src/shots.ts:217,231`); second-consumer
  proof (`app/demo/second-host.ts:233`).
- **Design tuning:** the first capture used a loose ring (factor 2) and the production fixture; it
  read as scattered cards. The final version uses a tight ring (factor 0.85) and a purpose-built
  1+4+12 tree, which shortens the ribbons and packs the rosette. `octaves-near` frames one ½× branch
  so the ¼× work cards become readable — the zoom half of the claim.
- **Evidence:** `pi/pi-agent-dynamic-range.png` (incumbent), `pi/pi-agent-octaves.png` (variant),
  `pi/pi-agent-octaves-near.png` (zoom evidence); pending decision `multi-octave-range` in
  `docs/screenshots/reports/graph-layout-comparison.json` and note-only entries in `review.json`.
- **Gates:** root typecheck/1047 tests, Pi `check:fast` 181, Pi screenshot capture 3/3, full vision
  suite 25/25 before the final radius tuning, then the graph-arrangement vision gate 1/1 after it.
  Default layout remains `freeform`; renderer code is untouched.
- **Open:** human verdict on `multi-octave-range`. If kept, the next step is a real task study —
  the screenshot proves the structure, not that the range helps anyone find anything.

## 9. Host boundary and screenshot organization

Implemented in §10. This section keeps the decisions and rationale; §10 records the landed work.

### 9.1 Where the multi-octave work should live

Recommendation: **split roles, do not move the existing work out of Pi**.

- Keep the generic `octaveLayout` helper, the opaque scale descriptor and the renderer-size seam in
  the library. They are already host-neutral and proven by a second consumer.
- Keep `?graphLayout=octaves` and its two named shots in Pi as the *real-data proof*. They already
  pass the vision, shell and screenshot gates. Removing them now would discard working evidence.
- Add a small **scale lab** page under `app/demo` (same pattern as `scenario.html`) as the *iteration
  environment*: URL knobs for radius factor, depth, ring vs spiral, phase, per-octave palette and
  incumbent/variant selection. It is a thin host over the same helper and renderer — not a second
  flagship, not a second position authority, no new renderer branch.
- Only a variant that wins in the lab should be promoted back into Pi as one more opt-in shot. This
  keeps experiment churn out of `GRAPH_LAYOUTS`, the Pi fixture selector and the flagship gallery.

Rationale: the current Pi shot needed a synthetic `1+4+12` fixture, a hull-suppression branch and a
graph-layout enum entry. That cost is acceptable once, not for every radius or palette tweak. The
lab is where those hypotheses should be cheap.

### 9.2 Screenshot organization

Current problem: 38 `pi/pi-agent-*.png` files plus `.prev` files sit at the root of
`docs/screenshots/`, mixed with generated atlases, per-experiment pairs and reports. Curated
evidence and disposable output are hard to tell apart.

Target layout (minimal-churn first step; deeper grouping is optional later):

```
docs/screenshots/
  pi/                     curated flagship shots, tracked
    *.png                 keep existing filenames in the first migration
    layout/               optional second step: chapters, octaves, timeline, dynamic-range
    chrome/               optional second step: ui-*, statusline, menus
  labs/                   generated experiment pairs, gitignored
    ui-presets/<id>/{incumbent,variant}.png
    scenario-workflow-chapters/{incumbent,variant}.png
    scale-lab/<variant>/{incumbent,variant}.png
  reports/                comparison.json files and baselines with stable names
  atlas/                  generated atlas frames (existing)
  demo-atlas/             generated demo atlas (existing, gitignored)
  README.md               tracked/generated conventions and regeneration commands
  index.html              top-level contact sheet linking per-section galleries
  experiments.json        experiment registry (see 9.3)
```

Migration must update every path reference, not just move files: `Shot.file` values,
`app/pi/scripts/shot.ts` output root, `app/pi/tests/ui-compare.spec.ts`, `app/pi/src/ui/evidence.ts`,
`app/demo/tests/scenario-compare.spec.ts`, `review.json` notes, all `comparison.json` image fields,
`docs/screenshots/README.md` and the contact-sheet generator. Preserve the `*.png.prev` ignore rule.

### 9.3 Preparing for experiments

Add `docs/screenshots/experiments.json` as the single index of pending work. One entry per
hypothesis: `id`, `host`, `status` (`pending|kept|rejected`), `hypothesis`, `incumbent`, `variant`,
`pair` paths, `command` to regenerate, and `decision` path. The contact sheet reads this file so a
pending verdict is visible instead of buried in prose. Rules:

1. Every new visual idea gets an id, one hypothesis sentence, one opt-in URL state, a deterministic
   fixture, a named shot or lab state, and an incumbent/variant pair — before it gets polish.
2. Generated pairs are gitignored; only curated winner shots are tracked. `.prev` files stay ignored.
3. A pair is regenerable by one documented command; no local-only image may support a verdict.
4. No default flip without a logged human decision (ADR 0008). `experiments.json` records the
   decision when it lands; it never writes one.
5. The lab exposes all knobs through URL state so a pair is exact and reproducible.

### 9.4 Fresh-session work order

1. Decide final directory names and whether to drop the `pi-agent-` prefix, then do one `git mv`
   pass plus the path-reference updates in 9.2.
2. Regenerate the Pi shots, UI pairs and scenario pair; verify the contact sheet and README.
3. Build the scale lab page with URL knobs and an incumbent/variant capture spec; add its first
   experiment entry to `experiments.json` and its pair directory under `labs/scale-lab/`.
4. Run the lab against several radius/depth values and choose one candidate, if any, to port back
   to Pi as a single opt-in shot.
5. Run the full verification set once, update §6/§8/§9 progress, and commit.

### 9.5 Constraints for that session

No default promotion, no renderer branch, no second position authority, no new flagship. Generated
output stays out of git. Keep the current Pi shots and gates green while the lab is introduced.

### 9.6 Decisions made

- Keep the `pi-agent-` filename prefix. The directory is the curator boundary; renaming 38 files
  would churn every table and note without adding information.
- Move curated shots into `pi/`, generated pairs into `labs/`, and tracked decisions/baselines into
  `reports/`. Generated pairs keep their comparison JSON beside the images. Landed in §10 and §12.
- The lab reuses the generic `octaveLayout` and one renderer. Its only library change is a
  `shape: 'ring' | 'spiral'` option on that helper; ring stays the default with byte-identical output.
- No candidate is promoted to Pi. ADR 0008 still requires a human verdict, and porting the step
  palette needs a separate host-side colour seam.
