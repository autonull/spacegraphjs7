## 1. Constraints

1. No default flip without a logged human verdict (ADR 0008). New visual work ships as opt-in URL
   state, a named shot, and an incumbent/variant pair.
2. No second position authority, renderer branch, or contract field for a visual idea. Helpers return
   positions or opaque `data`; hosts apply them through existing seams.
3. Library helpers take ids, sizes, edges and viewport. Run/turn/file/workflow vocabulary stays in
   `app/pi`, `app/demo` or generated scaffolds.
4. Pi test hooks stay stable: `#proof-line`, `#settings-menu > div`, `#surface-buttons`,
   `#depth-mode`, `#focus-primary`, `#attention`, `data-*` state (`tests/shell.spec.ts:23–55`).
5. A helper is "generic" only after a non-Pi host uses it with its own vocabulary and a test asserts
   the boundary (`second-host.test.ts` is the pattern).
6. Use `pnpm`; no fixed sleeps, no global mocks, no `any` in new code. Report failed gates as failed.
7. Human gates (TODO9 verdicts, study pilot) are dependencies, not developer tasks.

## 3. Execution

**Phase 0 — unblock and make chapters honest (S).** Do E1, B1, B2 and A1 together; they touch separate
files and share one verification run. E1 first: reproduce with a shortened preceding frame sequence,
then fix the cause or record the limit — never retry until green. B2 measures the packed layout (or
labels the simulated metric correctly). Exit: full visual gate result explained, corrected baseline,
new chapters frame with real internal work. Stop rule: if E1 requires a renderer change, split it into
its own plan before continuing.

**Phase 1 — compared opt-ins (M).** Do A2, B3, B4 and A3. Each visual item is one URL state, one shot
pair and one pending ADR 0008 stub. B4 is mandatory because stream stability is the reason
`previous` exists in `chapterPacking`. Exit: vision gate green, three pending pairs, no default flip.
Stop rule: if a pair cannot be captured deterministically, drop the variant rather than weaken the gate.

**Phase 2 — generalize with proof (M).** D1 is the external blocker for any promotion; proceed with C1
only for seams that already have a non-Pi consumer. Promote the shot/catalog shapes by extracting the
data shape and a thin adapter, not by moving Pi controls into the library. Exit: each promoted helper
has a `second-host.test.ts` (or equivalent) case and unchanged Pi e2e.

**Phase 3 — experiment workbench (L).** Start only after E1 is stable and C1 has landed. C2 adds one
`scenario.html` page driven by `?domain=&layout=&preset=`, using the existing domain packages and
generated registry. C3 extends `packages/create-spacegraph/templates/spine.ts` with the same five
pieces Pi owns today. C4 captures the two-domain proof pair. Blast radius before starting: demo
registry counts, demo-atlas frame count, scaffold output and publish-check fixtures all change —
announce and verify them together.

**Phase 4 — final gate and opportunistic cleanup (S).** E2 and E3 only if Phases 0–3 are green. One
final verification run, then record results in §6.

## 8. Follow-up experiment — multi-octave dynamic range (2026-11-23)

Requested after the plan closed: a layout that shows scale itself, not just one LOD at a time.

- **Hypothesis:** drawing one hierarchy at 1× / ½× / ¼× world scale in a single frame makes the
  self-similar structure visible at fit zoom, and zooming into one branch promotes its smallest
  cards to legible detail. This is the first experiment that changes node *size* rather than chrome.
- **Landed:** generic `octaveLayout(ids, parentOf, options)` at `src/layout/octaves.ts:29`, with a
  caller-owned parent map and no vocabulary; opaque per-node scale descriptors on `GraphLayout`
  (`src/layout/strategies.ts:130`); Pi adapter and opt-in mode `octaves`
  (`app/pi/src/graph-layout.ts:150,193`); host applies scale through the existing `size` seam and
  hides scope hulls in that mode (`app/pi/src/host.ts:283,1044,1129`); symmetric shot fixture
  (`app/pi/src/fixture.ts:123`); two named shots (`app/pi/src/shots.ts:217,231`); second-consumer
  proof (`app/demo/second-host.ts:233`).
- **Design tuning:** the first capture used a loose ring (factor 2) and the production fixture; it
  read as scattered cards. The final version uses a tight ring (factor 0.85) and a purpose-built
  1+4+12 tree, which shortens the ribbons and packs the rosette. `octaves-near` frames one ½× branch
  so the ¼× work cards become readable — the zoom half of the claim.
- **Evidence:** `pi-agent-dynamic-range.png` (incumbent), `pi-agent-octaves.png` (variant),
  `pi-agent-octaves-near.png` (zoom evidence); pending decision `multi-octave-range` in
  `docs/screenshots/graph-layout/comparison.json` and note-only entries in `review.json`.
- **Gates:** root typecheck/1047 tests, Pi `check:fast` 181, Pi screenshot capture 3/3, full vision
  suite 25/25 before the final radius tuning, then the graph-arrangement vision gate 1/1 after it.
  Default layout remains `freeform`; renderer code is untouched.
- **Open:** human verdict on `multi-octave-range`. If kept, the next step is a real task study —
  the screenshot proves the structure, not that the range helps anyone find anything.
